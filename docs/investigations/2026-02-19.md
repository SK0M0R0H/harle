# Investigation: Timeline Answer Missing Privacy Blocker

**Date:** 2026-02-19

**Goal of this file:** Use during implementation to understand priorities and what needs to be implemented so that follow-up questions correctly surface information from the conversation topic (e.g. privacy blocker in L3 roadmap).

---

## 1. Problem

User had a multi-turn chat with Harle:

1. **Q:** "Is there any blockers for building e-claim L3 solution on top of ADI?" → Answer listed several blockers (DA, compliance, resources, etc.).
2. **Q:** "What about privacy?" → Answer covered privacy considerations (GDPR, PHI, consent, etc.).
3. **Q:** "When it'll be possible to build?" → Answer gave a **timeline** (foundations March 2026, production May 2026, features mid-2026) but **did not mention the privacy blocker** or that privacy is scheduled for end of 2026 in the L3 roadmap.

**Expected behaviour:** The third answer should have tied the timeline to the **privacy blocker** (e.g. "building may be blocked or delayed until privacy is ready — end of 2026") because the user had just asked about privacy and the L3 roadmap states the privacy blocker at end of 2026.

**Actual behaviour:** The timeline response was based only on general L3 timeline content; the privacy blocker was not retrieved or emphasised.

---

## 2. Root Causes

### 2.1 Retrieval uses only the current message

The Search Algorithm is given **only the current user message** as the query. It does not receive conversation history or any expansion of the query.

- For "When it'll be possible to build?" the effective search terms are: `when`, `it'll`, `possible`, `build`.
- There is no "privacy", "blocker", "e-claim", or "L3" in the query.
- So retrieval has no signal that the user cares about the privacy blocker when answering "when".

**Code:** `src/harle/context/assembler.py` — `_search_dataset(message=message, ...)` is called with `message` only. `SearchQuery(query=message, ...)` is passed to the search engine.

### 2.2 Conversation history is not used for search

Conversation history is passed into the Context Assembler and used only as **P4 (background)** context: it is formatted and appended to the system prompt so the **LLM** sees prior turns. The **search** step never sees it.

- So retrieval does not know that the user previously asked "What about privacy?" and that the answer should connect "when to build" with "privacy blocker".

### 2.3 Query expansion is not implemented

The TRD (e.g. `docs/trd/architecture/data.md`) describes **query expansion** (Step 1): take the user request and optionally the agent role, and derive/enrich search terms (e.g. add "privacy", "blocker" when the last turn was about privacy).

- `src/harle/search/query_expander.py` exists but is a stub: "Query expansion — extract and enrich search terms (not yet implemented)."
- So there is no automatic way to pull "privacy" into the search when the user asks "when it'll be possible to build?".

### 2.4 Keyword-only search

The current search engine is keyword-based (tokenise message, score by term matches in title/tags/content). Semantic search (pgvector) is planned but not in place.

- Even if the L3 roadmap file is retrieved (e.g. due to "build", "possible", timeline terms), the specific sentence about "privacy blocker end of 2026" may sit in a long document and may not rank highly for the terms "when possible build", so it may be omitted or under-emphasised in the assembled context.

---

## 3. What needs to be implemented (priorities)

Use this section to prioritise and scope implementation.

### 3.1 High priority — conversation-aware retrieval

**Objective:** Follow-up questions like "When it'll be possible to build?" should retrieve content relevant to the **topic of the conversation** (e.g. privacy, blockers), not only to the literal words in the current message.

**Options:**

- **Option A — Use conversation history to expand the search query**  
  When assembling context, derive extra search terms from recent conversation (e.g. last user question + last assistant summary, or key nouns/entities from the last N turns) and merge them with the current message for retrieval.  
  - Delivers: same search API, richer query.  
  - Implementation: extend the path that builds `SearchQuery` (e.g. in Context Assembler or in a new query-expansion step) to accept optional `conversation_history` and produce an expanded `query` string (or structured terms) from current message + history.

- **Option B — Query expansion module (TRD Step 1)**  
  Implement the TRD’s "query expansion" step: input = user request + optional agent role + optional conversation summary; output = enriched set of search terms (and optionally tag filters).  
  - Then pass the **expanded query** (or terms) to the search engine instead of only `message`.  
  - Conversation-aware retrieval can be one source of expansion (terms from recent turns).

**Recommendation:** Implement query expansion (Option B) and use conversation history as one input to that expansion (Option A). That aligns with the TRD and keeps retrieval behaviour explicit and testable.

### 3.2 Medium priority — query expansion implementation

**Objective:** Replace the stub in `src/harle/search/query_expander.py` with a real expansion step.

- **Inputs:** Current message, context scope, optional conversation history (or a short summary of recent topic).
- **Outputs:** Enriched query string and/or list of terms (and optionally tags) for the search engine.
- **Behaviour:** At minimum, merge current message with salient terms from the last user/assistant turn (e.g. "privacy", "blocker") so that "When it'll be possible to build?" also searches for privacy/blocker when the conversation was about privacy.
- **Integration:** Context Assembler calls the expander before building `SearchQuery`, and passes the expanded query (and any filters) to the search engine.

### 3.3 Lower priority / existing roadmap

- **Semantic search (pgvector):** Helps when the roadmap says "privacy blocker" and the user says "when to build" with no shared keywords. Complements query expansion; already in TRD/data layer.
- **Reranking / contextual summaries:** So that the exact phrase "privacy blocker end of 2026" is more likely to be included when the expanded query includes "privacy" and "blocker"; see TRD and `main_challenges.md`.

---

## 4. User workaround (until implemented)

Ask in one shot so that the topic is in the search query, e.g.:

- "When will it be possible to build the e-claim L3 solution, **including the privacy blocker**?"

That way "privacy" and "blocker" are in the message and the roadmap section about the privacy blocker is more likely to be retrieved and used.
